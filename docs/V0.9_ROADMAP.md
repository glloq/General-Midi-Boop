**Conclusion de cadrage.** Le code est **structurellement sain**. Le travail
restant pour la v0.9 n'est **pas** de la correction de bugs cassants, mais de la
**complétude fonctionnelle** : le **modèle de données et la surface backend/UI
sont en avance sur le moteur et sur le câblage UI**. Trois écarts à combler :

1. **Écart moteur** — des capacités d'instrument sont persistées + validées mais
   jamais lues par le moteur de playback/routage.
2. **Écart UI** — des commandes/événements backend existent mais ne sont branchés
   à aucun composant d'interface.
3. **Reports V2 assumés** — quelques fonctionnalités volontairement verrouillées
   « V2 » (dont il faut décider si elles entrent dans le périmètre v0.9).

À cela s'ajoute la **QA runtime** (matériel Pi + navigateur) qui n'est pas
réalisable dans un sandbox et reste à faire par un humain.

## 1. Définition de « v0.9 = 100 % fonctionnel »

Un réglage exposé dans l'UI ou une donnée persistée en base **doit produire un
effet réel et correct** à l'exécution. Le critère d'acceptation de la v0.9 est
donc : **plus aucune capacité « morte »** (réglable/sauvegardée mais sans effet),
et **plus aucune fonctionnalité backend sans surface UI** (ou alors documentée
comme volontairement interne).

## T1 — Écart moteur : capacités persistées mais non consommées
*(source : `AUDIT_INSTRUMENT_CAPABILITIES_2026-08-05.md`, `INSTRUMENT_FAMILY_REFACTOR_ROADMAP.md` Phase 8)*

Ce sont les vrais blockers « 100 % fonctionnel » : l'utilisateur configure quelque
chose qui n'a **aucun effet** sur la sortie MIDI.

- [~] **T1.1 — Voix GM multiples : chemin playback livré + testé** 🟡 *(QA audio Pi restante)*
  **Fait & testé (21 tests) :** politique de sélection `VoiceSelector`
  (`selectVoiceProgram` / `planVoiceProgramChanges`, 16 tests) + injection
  `MidiPlayer._injectVoiceProgramChangeEvents` (5 tests, base factice sans
  SQLite natif). Politique retenue = **par plage/notes déclarées par voix**
  (gate `voices_share_notes=0`), exposée via `getInstrumentCapabilities`.
  Calquée sur l'injection hand-CC (même chemin `_routeTo` split-safe, marqueur
  `_voiceInjected` idempotent, `programChange` trié avant le `noteOn`).
  **No-op strict** (vérifié) si `voices_share_notes=1` ou aucune note par voix →
  zéro régression.
  **Restant :** (a) **QA audio sur Pi** (commutation de voix réelle sur
  matériel) ; (b) même injection pour le **route-through live** (`MidiRouter`,
  cas de jeu live, plus niche) ; (c) vérifier que l'éditeur par-voix
  (`voices_share_notes`) est exposé dans l'UI réglages.
  *(Ancien plan « bake » abandonné : les program-changes doivent atteindre le
  canal de l'instrument de destination — l'injection playback via `_routeTo`
  est le bon point, pas le bake sur canal source.)*
  Les colonnes `instrument_voices` (gm_program / min_note_* / supported_ccs, +
  range/selected_notes/octave_mode par voix via migration 005, gate
  `voices_share_notes`) sont écrites/validées mais **jamais lues** en
  playback/adaptation. → `MidiPlayer.js`, `MidiTransposer.js`, `InstrumentMatcher*.js`.
  **Deux bloqueurs pour livrer ici :**
  1. **Décision produit** — le schéma (`003_instrument_voices.sql`) dit
     explicitement « the engine picks ONE voice per note based on **context** »
     sans figer le signal (octave / vélocité / CC d'articulation / annotation).
     Livrer un défaut arbitraire serait un choix non validé.
     *Proposition concrète* : politique **par plage de notes déclarée par voix**
     (quand `voices_share_notes = 0` + plages par voix ⇒ chaque voix « réclame »
     ses notes ; sinon voix primaire — no-op, zéro régression). Non arbitraire :
     pilotée par des données explicites de l'utilisateur. À valider.
  2. **Intégration + QA** — l'insertion des `program_change` par voix se fait
     proprement en **offline (bake)**, mais recalcul des delta-times / sélection
     de piste + relecture doivent être testés contre une vraie DB (bindings
     absents du sandbox) et validés à l'oreille sur Pi. Non vérifiable ici.

- [x] **T1.2 — Contraintes de cordes appliquées à l'audible** ✅ (capo = décision conservée)
  `CapabilityResolver.getTimingConstraints` dérive désormais la plage jouable
  `[min(tuning), max(tuning)+frettes]` depuis la géométrie des cordes quand
  aucun `note_range` explicite n'est défini (instruments **frettés** ;
  `frets_per_string` respecté). Le `clampNote` du scheduler replie donc les
  notes au-dessus de la dernière frette dans la plage atteignable, au lieu de
  les émettre à leur hauteur d'origine. Tests : `capability-resolver.test.js`.
  → **`capo_fret`** : laissé inerte **volontairement** — retiré du converter en
  2026-04 (documenté `TablatureConverter.js:17-20`, « transposé à la source »).
  Reste un nettoyage de surface (T7 : retirer la colonne/UI morte), pas un blocker.

- [x] **T1.3 — Configs d'instruments : consommées par les vues (faux manque)** ✅ *(vérifié)*
  Vérification code : `bagpipe_config` / `accordion_config` / `harmonica_config`
  **sont** consommés — par les vues clavier virtuelles `BagpipeView`
  (`.drones`), `AccordionView` (`bass_system`/stradella…), `HarmonicaView`
  (`type`/`key`). Ce sont sémantiquement des réglages de **vue / jeu live**, pas
  des transformations de playback de fichier : injecter les drones d'une
  cornemuse dans un fichier qui les contient déjà les **doublerait**, et le
  blow/draw d'un harmonica ne change pas la hauteur des notes d'un fichier.
  L'audit vérifiait le moteur de playback (mauvais endroit pour ces configs de
  vue). → **Aucun changement de code** ; pas un blocker.

- [x] **T1.4 — `supported_ccs` filtré en sortie** ✅
  `CapabilityResolver` expose désormais `supportedCcs` (assaini 0-127) et le
  scheduler ne transmet un CC que s'il est déclaré — plus les CC de sécurité
  toujours autorisés (mode canal 120-127, Bank Select 0/32) et CC20/21 (leur
  propre gate). Non déclaré → tout passe (rétro-compatible).
  `PlaybackScheduler._isCCSupported` ; tests `playback-fidelity.test.js`.
  *(Le filtrage côté route-through live sera couvert par T1.5.)*

- [x] **T1.5 — Enforcement stateful sur le route-through live** ✅
  *(P2-3)* Nouvelle classe stateful partagée `NoteGate` (`NoteEnforcement.js`,
  réutilise `selectPolyphonyVictim`) : polyphonie (éviction keep-outer) +
  `min_note_interval` (par-canal si monophonique, par-pitch sinon), câblée dans
  `MidiRouter._enforceLiveLimits` après le clamp. Filtre aussi les CC non
  supportés côté live (complète T1.4). Tests : `note-enforcement.test.js`,
  `midi-router-capability-clamp.test.js`.
  ⚠️ *Comportement live modifié (peut brider/évincer des notes) → QA Pi (T9).*

- [x] **T1.6 — `comm_timeout` lu par la reconnaissance** ✅
  `DeviceManager._getCommTimeoutMs(name)` lit le plus grand `comm_timeout` parmi
  les canaux du device et l'utilise pour le timeout de réponse d'identité
  (`_sendAutoIdentity`), avec repli sur 5000 ms (premier contact / valeur
  absente). Tests : `devicemanager-auto-identity.test.js`.

- [x] **T1.7 — Faisabilité « frettes » utilise `hand_span_mm`** ✅
  *(P2-7 #2)* `_scoreHandPositionFeasibility` convertit désormais `hand_span_mm`
  en frettes (`-12·log2(1 − span/scale)`, reach au sillet = estimation
  conservatrice) quand `hand_span_frets` est absent → l'avertissement de shift
  n'est plus sauté. `scale_length_mm` (table `string_instruments`) est joint aux
  capacités via `getInstrumentsWithCapabilities`, avec repli 648 mm si absent.
  `InstrumentMatcher.js` + `InstrumentCapabilitiesDB.js` ; tests
  `instrument-matcher-hand-feasibility.test.js`.

- [ ] **T1.8 — Pipeline descripteur v2 partiellement câblé** ⚠️ *(sprint — nécessite QA DB réelle)*
  *(P2-2)* Le cœur est câblé ; restent ouverts : persistance DB du cache
  descripteur (survie au redémarrage), descripteur précédent pour le diff,
  persistance des surcharges utilisateur, chemin HTTP, valeur
  `capabilities_source='descriptor'`, et modélisation moteur du lookahead
  `timing.prepare` / `resources` / voix+polyphonie.
  **Bloqueur d'exécution ici** : passer `capabilities_source` à `'descriptor'`
  exige d'élargir la contrainte `CHECK(... IN ('manual','sysex','auto'))`
  (`001_baseline.sql:402`) → **rebuild de la table `instruments_latency`**
  (SQLite n'altère pas un CHECK en place). Une telle migration doit être
  vérifiée contre une vraie base (binding `better-sqlite3` absent du sandbox,
  suites de migration auto-skippées) — à faire dans un environnement avec DB.

- [x] **T1.9 — Identité SysEx écrite sur tous les canaux du device** ✅
  *(P1-3)* Nouveau `saveSysExIdentityForDevice(deviceId, identity)` (transaction)

## T3 — Divergences runtime ≠ offline (live vs baked)
*(source : `AUDIT_INSTRUMENT_CAPABILITIES_2026-08-05.md` P3-a…d)*

Le même fichier joué **en live** et **baké** ne produit pas le même résultat →
comportement non déterministe perçu par l'utilisateur.

- [x] **T3.1 — Drop polyphonique runtime = offline (P3-b)** ✅
  Le runtime applique désormais la même politique « garder grave+aigu, jeter le
  médian » que l'offline : sur dépassement de polyphonie, il évince la voix
  médiane (envoi note-off) au lieu de jeter systématiquement la dernière noteOn.
  Helper pur partagé `selectPolyphonyVictim` (`NoteEnforcement.js`), consommé par
  `PlaybackScheduler._shouldGateNote` (retour `{gate, evictNote}`) + éviction
  dans `_dispatchToDevice`. Tests : `playback-fidelity.test.js`.
  ⚠️ *Comportement audible modifié (coupe une voix qui sonne) → à valider en QA Pi (T9).*

- [x] **T3.2 — Repli de plage : sortie déjà identique (P3-c)** ✅ *(par conception)*
  Les deux chemins utilisent le **même** `foldIntoRange` → les notes émises sont
  déjà identiques live vs baked. Seule la **télémétrie** `compressionCollisions`
  reste offline-only (surface l'avertissement au moment de l'adaptation, là où
  l'utilisateur peut élargir la plage) — conservé volontairement.

- [x] **T3.3 — `selected_notes` ne sort plus de `note_range` (P3-d)** ✅
  `clampNote` filtre `selected_notes` au sous-ensemble dans `[min,max]` avant le
  snap ; si aucun n'est dans la plage, garde la note repliée (in-range).
  `NoteEnforcement.js` ; tests `note-enforcement.test.js`.

- [x] **T3.4 — `min_note_interval` par-mécanisme pour les monophoniques (P3-a)** ✅
  Pour un instrument monophonique (`polyphony === 1` = actuateur unique partagé),
  le garde de ré-attaque s'applique désormais **par canal** (deux hauteurs
  différentes en succession rapide sont bridées) ; les polyphoniques restent
  **par pitch** (préserve les accords). `PlaybackScheduler._shouldGateNote` ;
  tests `playback-fidelity.test.js`.
