## Synthèse

Le harnais navigateur qui manquait au projet **existe désormais** :
`tests/e2e/`, lançable en une commande (`node tests/e2e/run.mjs`), sans
matériel, sans modifier aucun fichier partagé. Il démarre son propre serveur sur
un port dédié avec une base jetable, pilote Chromium via **Playwright**,
enregistre erreurs console / erreurs réseau / WebSocket, mesure le tas via CDP,
capture des screenshots et écrit un `report.json` exploitable.

**Le scénario canonique passe 16 étapes sur 17.** La chaîne
`démarrage → instrument virtuel → import → assignation → adaptation → lecture →
ouverture de l'éditeur → sauvegarde → rechargement` fonctionne de bout en bout,
et l'instrument, le fichier et le routage **survivent au rechargement**. La
seule étape qui casse est la dernière : **l'édition ne survit pas, parce qu'elle
n'a jamais eu lieu** — le contrôle de tempo de l'éditeur MIDI lève une
`TypeError` non capturée à chaque frappe et n'applique rien (F-86).

Le harnais a produit, dès son premier passage, **dix findings dont aucun n'était
atteignable par les suites Jest/Vitest existantes** : un contrôle mort qui jette
en silence, quatre modales sur cinq qui fuient écouteurs et nœuds DOM à chaque ouverture, un
rechargement de page qui laisse l'orchestre jouer sans plus aucun moyen de
l'arrêter, deux calques qui bloquent tous les clics, un bouton Stop qui ne se
désactive jamais, des chaînes françaises en dur dans une UI en anglais — et
surtout la **mesure chiffrée du blocage F-14** : le `document.write` vers le CDN
bloque le parsing du document **1:1 avec le délai réseau**, soit 8,4 s mesurées pour 8 s de timeout injecté, et
3,4 s pour 3 s — un surcoût constant de ~420 ms sur un blocage qui suit le
réseau à l'identique.

## 1. Voie technique retenue

**Playwright**, pas le pilotage CDP brut.

L'énoncé prévoyait un repli sur le protocole CDP + le module `ws` si Playwright
était absent de `node_modules`. Vérification faite :

```
$ ls /opt/pw-browsers
chromium  chromium-1194  chromium_headless_shell-1194  ffmpeg-1011

$ ls node_modules | grep -i playwright        # → rien

$ npm ls -g --depth=0 | grep playwright
+-- playwright@1.56.1
```

Playwright **est** disponible, en installation globale. Le piège est qu'ESM
**ignore `NODE_PATH`** : `import('playwright')` échoue depuis un `.mjs` même
avec `NODE_PATH=/opt/node22/lib/node_modules`. La résolution passe donc par le
chemin absolu du point d'entrée du paquet. `tests/e2e/lib/playwright.mjs`
encapsule cela en trois essais successifs :

1. `import('playwright')` — dépendance locale (chemin normal une fois le
   `devDependency` ajouté, cf. §7) ;
2. `$PLAYWRIGHT_MODULE` — surcharge explicite ;
3. `npm root -g` puis une liste de préfixes globaux connus.

Résultat au premier passage :

```
playwright : /opt/node22/lib/node_modules/playwright/index.mjs
chromium   : 141.0.7390.37
```

**Décision annexe : pas de `@playwright/test`.** Le harnais n'utilise que la
*bibliothèque* d'automatisation, jamais le *runner*. Deux raisons :

- il doit tourner depuis un dépôt sans Playwright local, ce qu'un runner installé
  globalement ne permet pas proprement ;
- un harnais d'audit a besoin d'un **journal étape par étape**. Le runner maison
  (`tests/e2e/lib/runner.mjs`, ~150 lignes, zéro dépendance) fournit
  `ctx.step()` : quand le scénario meurt à l'étape 8, les étapes 1 à 7 restent
  marquées PASS dans le rapport. C'est exactement ce qui transforme « le test est
  rouge » en « le parcours casse ici, précisément ».

## 2. Ce que le harnais couvre — et ne couvre pas

### Couvert

| Capacité | Où |
|---|---|
| Démarrage/arrêt d'un serveur jetable, port dédié, **base réinitialisée à chaque run** | `lib/server.mjs` |
| Attente de disponibilité réelle (`/api/health`), jamais un `sleep` | `lib/server.mjs` |
| Capture des **erreurs console**, `pageerror`, requêtes échouées, réponses ≥ 400, ouverture/fermeture WebSocket | `lib/browser.mjs` |
| **Screenshots** à chaque étape signifiante et en cas d'échec | `lib/browser.mjs` |
| Mesure du tas et des listeners via **CDP** (`Runtime.getHeapUsage`, `Performance.getMetrics`) + GC forcé | `lib/browser.mjs` |
| Objets de page : tous les sélecteurs SPA en un seul fichier | `lib/app.mjs` |
| Fixtures MIDI générées avec la dépendance `midi-file` du projet | `fixtures/make-midi.mjs` |
| Rapport machine `artifacts/report.json` (test × étape × preuve) | `run.mjs` |
| Exécution en une commande, code de sortie = nombre d'échecs | `run.mjs` |

Le harnais **n'écrit rien hors de `tests/e2e/artifacts/`**. En particulier il
force `GMBOOP_API_TOKEN` : sans cela `ApiTokenManager` génère un token et
**l'écrit dans le `.env` du dépôt**, ce qu'un run de test ne doit jamais faire.
La précaution s'est révélée fondée : un `.env` est bien apparu à la racine
pendant cette session d'audit, créé par le serveur d'un autre lot — pas par
celui-ci.

### Non couvert (et pourquoi)

| Trou | Raison |
|---|---|
| **Sortie MIDI réelle** | Pas de `libasound2-dev`, pas de matériel. Le harnais valide que le backend émet vers `virtual_…`, pas que des octets sortent d'un port USB. Reste §BJ / lot L15. |
| **Audio rendu** | `WebAudioFontPlayer` est indisponible (F-87/F-93) ; même chargé, comparer un rendu audio demande un banc dédié. |
| **Interaction fine du piano-roll (§Q01)** | Le glisser/redimensionner/sélectionner sur `<canvas>` n'est pas encore scripté. Le harnais ouvre l'éditeur, vérifie le rendu (3 canvas, 7 chips de canaux) et pilote les contrôles DOM. La brique manquante est un repérage de note par lecture de pixels : prototypée pendant l'audit, non retenue faute de fiabilité (elle attrapait la règle temporelle). **C'est l'extension n°1 à écrire.** |
| **Responsive / §AO** | Un seul viewport (1600×1000). Ajouter des contextes en 768 et 375 px est mécanique une fois le harnais en place. |
| **Accessibilité automatisée (§AR)** | Deux constats a11y sont tombés « par accident » (F-89, F-92) via le hit-testing. Un vrai passage demande axe-core injecté ; non fait. |
| **Charges XSS automatisées (§AI)** | Prévu par R3 mais non abordé, faute de temps. Le harnais est prêt à les porter. |
| **Multi-onglets / concurrence** | Un seul contexte navigateur par test. |

Commande, reproductible telle quelle :

```bash

```

```

  specs      : 01-boot, 02-canonical, 03-modal-memory, 04-resilience

  server up  : 460 ms
  playwright : /opt/node22/lib/node_modules/playwright/index.mjs
  chromium   : 141.0.7390.37
```

Le serveur démarre en **~0,5 s** et sert la SPA sans matériel : la prémisse de
R3 (« les conditions sont favorables ») est confirmée par la mesure.

### 3.1 — Démarrage (`01-boot`)

| Test | État | Preuve |
|---|---|---|
| La SPA démarre, se connecte, devient interactive | **PASS** | 5 519 ms jusqu'à `#app:not(.hidden)` + WebSocket `readyState 1` |
| Le player WebAudioFont vendorisé est servi | **FAIL** | → **F-88** |
| Démarrage CDN injoignable — mesure du blocage | **FAIL** | → **F-87** |

Détail du temps d'accès : sur les 5 519 ms, **4 000 ms sont un plancher
volontaire** — `index.html` maintient l'écran de chargement au minimum 4 s quand
`localStorage` est vide (`setTimeout(hideLoading, 4000 - elapsed)`). Le boot réel
est donc de l'ordre de 1,5 s. C'est un choix produit, pas un défaut, **mais il
impose à tout harnais d'attendre `#app:not(.hidden)` et non `load`** : c'est
documenté dans `lib/app.mjs`.

Le parcours exigé par le plan, une étape enregistrée par stade :

**Verdict : 16 étapes sur 17 passent (1 avertissement, 1 échec). La rupture est
unique et nette — l'édition n'est jamais appliquée.** Preuve directe, lue dans
l'état du composant au moment de la frappe :

```json
{ "shown": "84", "modalTempo": 120, "isDirty": false }
```

L'`<input>` affiche la valeur saisie (comportement natif du navigateur), le
composant conserve `120`, et `isDirty` reste `false` — donc la sauvegarde
n'écrit rien de nouveau. C'est **F-86**, décrit en §4.

L'étape 7c est enregistrée en **WARN** et non en FAIL, délibérément : elle
n'interrompt pas le parcours, pour que le rapport puisse dire si la sauvegarde,
le rechargement et la vérification fonctionnent — ils fonctionnent. Le défaut
lui-même n'est pas dissimulé pour autant : il est asserté durement deux fois, à
l'étape 10d (bout en bout) et dans un test dédié.

Deux autres tests de cette suite échouent, isolés exprès pour ne pas masquer les
étapes 8→10 :

- « le contrôle de tempo applique le tempo affiché » → **FAIL** (F-86) ;
- « les boutons du transport reflètent l'état de lecture » → **FAIL** (F-90).

### 3.3 — Fuite de listeners / mémoire (`03-modal-memory`)

Protocole : 3 cycles d'échauffement (la première ouverture alloue légitimement :
templates, canvas, i18n), GC forcé, mesure de référence, puis **20 cycles
ouverture/fermeture** avec relevé tous les 4 cycles, GC forcé avant chaque
relevé, et delta final sur trois axes : tas vivant, `JSEventListeners`, `Nodes`.

| Modale | État | Δ listeners/cycle | Δ nœuds/cycle |
|---|---|---|---|
| KeyboardModal | **FAIL** | **+18** | **+603** |
| InstrumentManagementPage | **FAIL** | **+35** | **+276** |
| LoopCreatorModal | **FAIL** | **+5** | **+476** |
| PlaylistPage | **FAIL** | **+8,95** | **+74** |
| SettingsModal | **PASS** | 0 | +3,1 |

**Quatre modales lourdes sur cinq fuient → F-95.** `SettingsModal`, strictement
plate à 0 écouteur sur 20 cycles, est ce qui rend les quatre autres concluantes :
la méthode ne produit pas de faux positif systématique.

> **Un faux vert a été corrigé en cours de route.** La première version de ce
> spec utilisait des sélecteurs racines lâches du type
> `[class*="loop-creator"]` — qui matchent le **bouton d'en-tête**
> (`btn-loop-creator-toggle`), pas la modale. `waitForSelector` réussissait donc
> instantanément sans que rien ne s'ouvre, et le test annonçait « 0 fuite,
> 8/8 cycles ». Les sélecteurs racines sont désormais les éléments réellement
> ajoutés au `<body>`, relevés en direct, et le harnais **échoue explicitement**
> si la modale ne s'ouvre pas pendant l'échauffement plutôt que de rapporter un
> zéro rassurant. Avec les bons sélecteurs, `LoopCreatorModal` et `PlaylistPage`
> sont passées de « saines » à « fuyantes » : **deux findings avaient été perdus
> par un sélecteur trop permissif.** C'est le principal enseignement de méthode
> de ce lot.

### 3.4 — Résilience (`04-resilience`)

**Coupure du WebSocket en pleine lecture — PASS.** Le harnais ferme la socket
sous-jacente (`window.api.ws.close(4000)`) et non `api.close()` : ce dernier
positionne `_closed` et **court-circuite toute la logique de reconnexion**, ce
qui aurait rendu le test faussement vert.

```
disconnected  +0 ms
reconnecting  +1 ms
connected     +1 020 ms
```

Bandeau affiché pendant la coupure : « **Reconnexion** ». La reconnexion est
automatique, conforme au back-off documenté (délai de base 1 s), et l'UI
redevient pleinement utilisable ensuite (`device_list` répond). **C'est le
mécanisme de résilience le mieux tenu du produit sur ce périmètre.**

> Deux précisions de méthode. (a) Le libellé « Reconnexion » apparaît alors que
> la locale est `en` — nouvelle occurrence de **F-91**. (b) Une première version
> du test échantillonnait le DOM une seule fois après la coupure et concluait
> « aucun retour utilisateur » : la reconnexion étant plus rapide (1 s) que
> l'échantillon, le bandeau avait déjà disparu. Le spec observe désormais le DOM
> à 10 Hz pendant toute la fenêtre de coupure. **Sans cette correction, le
> harnais aurait produit un finding inexistant** — un rappel utile que la
> précision d'un harnais se paie.

**Rechargement en pleine lecture — FAIL → F-94.** Le backend continue de jouer
(`playing: true, position: 6,15 s`), la SPA rechargée affiche
« No file selected », Stop désactivé. Détail en §4.

## 4. Findings

### F-86 — P1 — Le contrôle de tempo de l'éditeur MIDI est mort et jette une `TypeError`

**Section :** §Q01, §BI, §D (éditeur MIDI) · **État : CONFIRMÉ, reproductible**

`MidiEditorEvents.js` câble l'input de tempo sur `this.modal.setTempo(...)` :

```js
// public/js/features/midi-editor/MidiEditorEvents.js:220 et :233
tempoInput.addEventListener('change', (e) => { … this.modal.setTempo(newTempo); });
tempoInput.addEventListener('input',  (e) => { … this.modal.setTempo(newTempo, { silent: true }); });
```

Or `setTempo()` vit sur le sous-composant `MidiEditorEditActions`
(`MidiEditorEditActions.js:190`), et **`MidiEditorModal` n'expose aucun délégué
`setTempo`**. Le retrait des mixins (P2-F.10a→l) a ajouté des délégués pour
`toggleTouchMode` / `toggleKeyboardPlayback` / `toggleDragPlayback`
(`MidiEditorModal.js:744-753`, avec un commentaire qui décrit exactement ce
risque : « without these delegates, the modal exposes no method and the click is
a TypeError ») — **mais a oublié `setTempo`**. Tous les autres appels de
`MidiEditorEvents` passent par `this.modal.editActions?.X()` ; celui-ci est le
seul à viser la modale directement.

**Conséquence, mesurée dans le navigateur :**

| Observé | Valeur |
|---|---|
| Valeur affichée par l'input | `84` (ou `96`) |
| `modal.tempo` après la frappe | `120` — inchangé |
| `modal.isDirty` | `false` — la sauvegarde ne considère rien comme modifié |
| Exceptions non capturées | 3 par édition (`input` ×2 + `change`) |
| Tempo relu après sauvegarde + rechargement | `120` |

Le tempo n'est donc **jamais** appliqué : ni au piano-roll, ni au synthétiseur,
ni au fichier sauvegardé. L'utilisateur voit sa valeur dans le champ, ne reçoit
aucun message d'erreur, sauvegarde, recharge — et retrouve l'ancien tempo. C'est
la seule rupture du scénario canonique.

**Reproduction :**

```bash
PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers node tests/e2e/run.mjs 02
# → FAIL "the MIDI editor's tempo control applies the tempo it displays"
```

**Correctif suggéré** (au lot propriétaire de l'éditeur — non appliqué ici) :
ajouter le délégué manquant à côté des trois existants dans
`MidiEditorModal.js`, ou corriger les deux appels de `MidiEditorEvents.js` en
`this.modal.editActions?.setTempo(...)`, cohérent avec les 10 autres appels du
même fichier.

> **Classe de bug, pas cas isolé.** 19 noms distincts sont appelés en
> `this.modal.X()` depuis `public/js/features/midi-editor/*.js` :
> `_saveTouchModePref · close · getInstrumentName · log · playbackPause ·
> playbackPlay · playbackStop · refreshChannelButtons · setTempo · showError ·
> showErrorModal · showNotification · syncMutedChannels · t · tHtml ·
> toggleDragPlayback · toggleKeyboardPlayback · togglePlayback · toggleTouchMode`.
> Un seul a été vérifié à l'exécution (`setTempo`, cassé). **Le balayage complet
> de cette liste est la première tâche recommandée au lot éditeur** ; le harnais
> est prêt à l'automatiser (capture de l'instance via un patch de
> `MidiEditorModal.prototype.log`, puis `typeof inst[nom] === 'function'` pour
> chaque nom).

### F-87 — P1 — `document.write` vers le CDN : le parsing bloque 1:1 avec le délai réseau

**Section :** §AD (offline-first), §AU · **État : CONFIRMÉ — mesure navigateur de F-14**

`public/index.html:6009-6013` :

```html
<script src="lib/WebAudioFontPlayer.js"></script>
<script>
  if (typeof WebAudioFontPlayer === 'undefined') {
    document.write('<scr' + 'ipt src="https://surikov.github.io/…/WebAudioFontPlayer.js"><' + '/scr' + 'ipt>');
  }
</script>
```

L00 a confirmé le finding statiquement ; L14 a montré qu'il est **aggravé** en
production (`dist/` omet `lib/`, donc la vendorisation hors-ligne est annulée).
Ce lot apporte la **mesure**.

**Protocole.** Le proxy du conteneur refuse la requête CDN en ~30 ms
(`ERR_TUNNEL_CONNECTION_FAILED`), ce qui masquerait complètement le problème : un
Pi réellement hors-ligne n'obtient pas un refus rapide, il attend l'expiration
DNS/TCP. Le harnais intercepte donc l'URL du CDN et la fait **traîner** un délai
paramétrable, puis échouer — ce qui reproduit un réseau qui ne répond pas.

**Résultat, délai injecté 8 000 ms :**

| Mesure | Valeur |
|---|---|
| Requête CDN effectivement émise | **oui** (1×) — le chemin `document.write` est bien vivant |
| `DOMContentLoaded` | **8 421 ms** |
| Temps jusqu'à l'état interactif | **12 777 ms** |
| Référence sans blocage (même machine) | 5 519 ms, dont 4 000 ms de plancher d'écran de chargement |
| `typeof WebAudioFontPlayer` après échec | `"undefined"` |

**Le blocage est linéaire par rapport au délai réseau**, vérifié sur deux
points :

| Délai CDN injecté | `DOMContentLoaded` | Surcoût |
|---|---|---|
| 3 000 ms | 3 424 ms | +424 ms |
| 8 000 ms | 8 421 ms | +421 ms |

Le surcoût est constant (~420 ms, le reste du parsing) et **le temps perdu suit
le délai réseau à l'identique**. Le script inséré par `document.write` est
*parser-blocking* ; le document entier reste `readyState === 'loading'` jusqu'à
ce que la requête aboutisse ou échoue. Chromium l'annonce d'ailleurs lui-même :

```
[warning] A parser-blocking, cross site script,
https://surikov.github.io/webaudiofont/npm/dist/WebAudioFontPlayer.js,
is invoked via document.write.
```

Sur un Pi hors-ligne où la résolution DNS expire à 30 s, **la SPA est inutilisable
pendant ~30 s à chaque chargement**, sur un produit dont le premier argument est
« offline-first ». Et à l'issue de l'attente, `WebAudioFontPlayer` reste
`undefined` : l'attente n'a servi à rien (cf. F-93).

Le correctif revient au lot L11 ; le paramètre de mesure est
`E2E_CDN_STALL_MS` si l'on veut vérifier d'autres seuils.

### F-94 — P1 — Rechargement en pleine lecture : l'orchestre continue, l'UI perd tout contrôle

**Section :** §AN, §BW · **État : CONFIRMÉ, reproductible**

Scénario : fichier routé, lecture lancée, puis `F5` au milieu du morceau.
Mesure faite immédiatement après que la SPA a fini de redémarrer :

| Source | Ce qu'elle dit |
|---|---|
| Backend `playback_status` | `playing: true`, `position: 6.15 s / 15.98 s`, `outputDevice: virtual_…` |
| En-tête de la SPA rechargée | `stopDisabled: true`, `file: "No file selected"`, bouton `▶️ Play` |

**Le backend continue de jouer ; l'interface rechargée l'ignore totalement.**
Elle n'affiche ni le nom du fichier, ni la position, et surtout **elle n'offre
aucun bouton Stop** — celui-ci est désactivé, puisqu'elle croit qu'il ne se passe
rien. Il n'existe donc plus, depuis l'UI, aucun moyen d'arrêter la lecture en
cours : ni Stop, ni pause, ni panic accessible depuis l'en-tête.

Sur un appareil de scène, cela signifie qu'un rafraîchissement accidentel du
navigateur — ou un onglet rouvert, ou un plantage de l'onglet — **fait perdre le
contrôle de l'orchestre pendant toute la durée du morceau**.

Le correctif n'est pas nécessairement « reprendre la lecture » : il suffit que la
SPA interroge `playback_status` à la connexion et rétablisse l'en-tête en
conséquence. Le backend expose déjà tout ce qu'il faut (fichier, position, durée,
device) ; c'est un raccordement manquant côté client, pas une donnée absente.

> **Piège de mesure.** Une première exécution de ce test était verte, parce que
> le test précédent de la même suite avait laissé le backend à l'arrêt : le
> rechargement n'avait alors rien à perdre. Le harnais force désormais un
> `playback_stop` en préparation, et le défaut apparaît systématiquement. C'est
> le genre de faux vert qu'un harnais partagé produit facilement — d'où la règle
> « ne jamais laisser un test dépendre de l'état laissé par le précédent »
> ajoutée au README.

### F-95 — P2 — Quatre modales lourdes sur cinq fuient à chaque ouverture

**Section :** §AV · **État : CONFIRMÉ, mesuré**

Protocole : 3 cycles d'échauffement, GC forcé, référence, puis 20 cycles
ouverture/fermeture avec relevé tous les 4 cycles et GC forcé avant chaque
mesure. Trois axes : tas vivant (`Runtime.getHeapUsage`), `JSEventListeners` et
`Nodes` (`Performance.getMetrics`).

| Modale | Δ listeners / cycle | Δ nœuds DOM / cycle | Verdict |
|---|---|---|---|
| **KeyboardModal** | **+18** | **+603** | **FUITE** |
| **InstrumentManagementPage** | **+35** | **+276** | **FUITE** |
| **LoopCreatorModal** | **+5** | **+476** | **FUITE** |
| **PlaylistPage** | **+8,95** | **+74** | **FUITE** |
| SettingsModal | 0 | +3,1 | sain |

Sur 20 cycles, cela représente **+360 écouteurs et +12 060 nœuds** pour
`KeyboardModal`, **+700 écouteurs** pour `InstrumentManagementPage`, **+9 512
nœuds** pour `LoopCreatorModal`.

La progression est parfaitement linéaire, ce qui exclut le bruit de mesure.
Relevé brut de `KeyboardModal` (8 cycles, la série de 20 est identique en pente) :

```
3.68 MB · 247 listeners · 4927 nodes   ← référence
3.70 MB · 264 listeners · 5521 nodes
3.73 MB · 281 listeners · 6115 nodes
3.74 MB · 298 listeners · 6709 nodes
3.75 MB · 315 listeners · 7303 nodes
3.77 MB · 332 listeners · 7897 nodes
3.86 MB · 349 listeners · 8491 nodes
3.87 MB · 366 listeners · 9085 nodes
3.90 MB · 383 listeners · 9679 nodes   ← +136 listeners, +4 752 nœuds en 8 cycles
```

Cause immédiate observée pour `KeyboardModal` : **le nœud `div.keyboard-modal`
n'est jamais retiré du `<body>`.** Après un Échap, il est toujours présent dans
l'arbre (vérifié en direct : `after Escape still present: ['DIV.keyboard-modal']`).
Chaque ouverture en empile donc un nouveau, avec ses écouteurs.

coût réel est le **nombre de nœuds** — 594 par ouverture — qui alourdit chaque
recalcul de style et chaque parcours du DOM. Sur un Pi 4, avec un clavier virtuel
ouvert et refermé quelques dizaines de fois pendant une session, on atteint
plusieurs dizaines de milliers de nœuds fantômes, et les 17 écouteurs par cycle
continuent de recevoir des événements que plus personne n'affiche.

`SettingsModal` montre que le projet sait faire : `BaseModal` fournit le
mécanisme de nettoyage, les quatre autres ne s'en servent pas (ou pas
complètement). C'est donc **une correction de fond à faire une fois**, pas quatre
correctifs indépendants.
