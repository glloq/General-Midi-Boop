## 🔴 Bugs et risques critiques

### 1. Collision de version sur la migration 016 — colonne `custom_sf2_id` jamais créée
**Catégorie** : correctness / contracts
**Localisation** : `migrations/016_has_lyrics.sql`,
`migrations/016_instrument_sf2.sql`,
`src/persistence/Database.js:117-123` (runner).

Le runner extrait le numéro de version avec
`parseInt(file.split('_')[0], 10)` puis `if (this.hasMigration(version)) continue;`.
Les deux fichiers retournent `version = 16`. `readdirSync().sort()`
applique `016_has_lyrics.sql` en premier (ordre ASCII), qui contient
`INSERT OR IGNORE INTO schema_version (version, description) VALUES (16, …)`.
Au passage suivant, `hasMigration(16)` est vrai → `016_instrument_sf2.sql`
est **silencieusement sauté**. Le `ALTER TABLE instruments_latency ADD
COLUMN custom_sf2_id …` ne tourne jamais.

Conséquence : `InstrumentSettingsDB.js:50` et `:283` écrivent dans une
colonne inexistante sur tout fresh install ; toute la feature SF2
par-instrument tombe à la première écriture.

**Fix** : renommer `016_instrument_sf2.sql` en `017_instrument_sf2.sql`
et décaler 017+ d'un cran ; OU créer une migration `019_fix_sf2_column.sql`
qui re-applique l'ALTER avec `ADD COLUMN IF NOT EXISTS`-équivalent
(better-sqlite3 attrape `duplicate column name` via le filet existant
ligne 182).

```js
// src/persistence/Database.js:117-123
for (const file of migrationFiles) {
  const version = parseInt(file.split('_')[0], 10);
  if (!Number.isFinite(version)) continue;
  if (this.hasMigration(version)) continue;  // ← skip basé sur le numéro
  this.runMigration(version, file, migrationsDir);
}
```

### 2. `MidiRouter` n'est pas détruit au shutdown
**Catégorie** : correctness / archi
**Localisation** : `src/core/Application.js:539-621` (`stop()`),
`src/midi/routing/MidiRouter.js:543-554` (`destroy()`).

`Application.stop()` détruit `eventLoopMonitor`, `backupScheduler`,
`midiPlayer`, `autoAssigner`, `compensationService`, `capabilityResolver`
— mais **omet** `midiRouter.destroy()`. Or `MidiRouter` maintient
`this.pendingTimeouts` (`Set<NodeJS.Timeout>`) pour la compensation
latence ; sans clear, les timers tirent après le close du
`deviceManager`, ce qui produit des `sendMessage` sur des ports MIDI
fermés (best-case warn, worst-case throw dans `node-midi`).

**Fix** : ajouter dans `Application.stop()`, juste avant
`if (this.database)` :
```js
if (this.midiRouter) this.midiRouter.destroy();
```

### 3. `unhandledRejection` tue le process
**Catégorie** : correctness / observabilité
**Localisation** : `src/core/Application.js:699-702`.

```js
const onUnhandled = (reason) => {
  this.logger.error(`Unhandled rejection: ${reason}`);
  shutdown('unhandledRejection').catch(() => process.exit(1));
};
```

Le code amorce un shutdown complet pour toute promesse rejetée hors
`try/catch`. C'est trop agressif pour un serveur long-running : une
lib tierce (Noble, serialport, dgram…) qui balance une rejection
bénigne tue toute la stack MIDI. La convention Node depuis v15 est
de logger et continuer ; le futur `--unhandled-rejections=throw`
gère déjà le worst-case.

**Fix** : remplacer par un `logger.error` sans `shutdown(...)`. Garder
le shutdown automatique uniquement pour `uncaughtException`.

### 4. `FilterManager.destroy()` jamais appelé → fuite timers + listeners
**Catégorie** : perf / correctness
**Localisation** : `public/js/utils/FilterManager.js:682-687`,
0 callers (`grep -rn "filterManager.destroy"` retourne vide).

`destroy()` existe et fait le job (clear des `debounceTimers`,
des handlers DOM), mais aucune page (`PlaylistPage`, `FileListPage`…)
ne l'appelle au démontage. À chaque navigation entre pages, les
listeners + 300 ms de timers debounce restent attachés. TODO.md le
mentionne déjà (« timers debounce non annulés »).

**Fix** : appeler `this.filterManager?.destroy()` dans le
`onLeave`/`onHide` des pages qui l'instancient. Lister via
`grep -n "new FilterManager"`.

### 5. WebSocket sans authentification si `GMBOOP_API_TOKEN` non défini
**Catégorie** : security
**Localisation** : `src/api/WebSocketServer.js:88-127`.

```js
verifyClient: apiToken
  ? ({ req }, done) => { /* … check token … */ }
  : undefined
```

Quand `GMBOOP_API_TOKEN` est absent (cas par défaut sur un fresh
install si `ApiTokenManager.ensure()` échoue ou ne setExports pas la
variable d'env du process avant la création du WS server), `verifyClient`
vaut `undefined` ; `ws` accepte alors **toute** connexion, y compris
externe. Le risque dépend de l'exposition réseau (LAN/WAN) du Pi.

**À vérifier** : confirmer que `new ApiTokenManager(this.logger).ensure()`
(Application.js:193) injecte bien la variable dans `process.env` du
process courant *avant* que `new WebSocketServer(deps, null)` ne soit
construit en ligne 346 — c'est synchrone, donc OK *si* `ensure()` écrit
sur `process.env.GMBOOP_API_TOKEN`. Auditer `ApiTokenManager.ensure()`
pour confirmer.

**Fix** : si le token est manquant, faire échouer `start()` (refus
fail-closed) plutôt que d'accepter tout le monde.

## 🟠 Risques et points d'attention

### 6. `versionedHandlers` = code mort
**Catégorie** : archi / contracts
**Localisation** : `src/api/CommandRegistry.js:74,91-103,184-188`.

`registry.register(name, handler, version)` est l'unique API qui
peuple `versionedHandlers`. Aucun appel avec un troisième argument
dans tout `src/api/commands/*`. Le dispatch dans `handle()` paie le
coût d'un `message.version && …` à chaque commande, sans bénéfice.

**Fix** : supprimer le paramètre `version` de `register()`, la branche
versionnée, et l'attribut `message.version` dans la réponse — ou
documenter explicitement que c'est un hook futur et le couvrir d'un
test.

### 7. CommandRegistry log INFO sur chaque commande WS
**Catégorie** : observabilité / perf
**Localisation** : `src/api/CommandRegistry.js:166, 194, 199, 217`.

Quatre `logger.info` par commande WS reçue (« Handling command »,
« Executing handler », « Handler executed, sending response »,
« Command completed in Xms »). La convention codifiée dans
`src/core/Logger.js:36-62` dit explicitement « un INFO = un jalon
opérateur, pas une itération ». À 60 commandes/s (le rate-limit),
c'est 240 lignes/s en INFO.

**Fix** : passer ces quatre lignes à `debug`. Garder un INFO unique
en cas d'erreur (déjà présent en ligne 229).

### 8. `ScoringConfig.typeDetection` somme à 130 (et non 100)
**Catégorie** : correctness
**Localisation** : `src/midi/adaptation/ScoringConfig.js:25-32`.

`40 + 25 + 20 + 15 + 30 = 130`. La doc en tête de fichier annonce
« total = 100 ». Les `weights` (haut) ont été corrigés à 100 par un
commit précédent, mais `typeDetection` est resté hors normalisation.
TODO.md flag déjà ce point, à confirmer comme une intention vs un bug.

**Fix** : soit normaliser à 100, soit reformuler le commentaire de
tête pour clarifier que `typeDetection` n'est pas borné à 100.

### 9. Pas de filtrage path/filename sur `file_rename` et `file_move`
**Catégorie** : security / contracts
**Localisation** : `src/api/commands/schemas/file.schemas.js:17-33`,
`src/files/FileManager.js:441-457`.

Le schéma valide la présence de `newFilename`/`folder` mais pas leur
contenu. Les valeurs vont directement dans la colonne `filename` /
`folder` de la DB. Aujourd'hui les blobs sont content-addressed donc
pas de path traversal disque, mais d'autres consommateurs (export
HTTP, filtre par dossier, broadcast aux clients) lisent ces champs.
Un `newFilename = "../../etc/passwd"` ou contenant des bytes de
contrôle finit affiché côté UI.

**Fix** : ajouter au schéma une regex stricte
(`^[^\x00-\x1f\\/]{1,255}$`) ou réutiliser
`JsonValidator.sanitizeString` côté handler.

### 10. `MidiRouter.broadcastMonitorEvent` fait un lookup DB par message
**Catégorie** : perf
**Localisation** : `src/midi/routing/MidiRouter.js:447-466`.

```js
const settings = db.getInstrumentSettings(deviceId, msg.channel);
```

Quand le moniteur global ou un moniteur per-device est actif,
**chaque** message MIDI (note on/off, CC à fréquence élevée) déclenche
une prepare-and-get SQLite. Le cache de `CapabilityResolver` /
`compensationService` n'est pas exploité.

**Fix** : utiliser `capabilityResolver` ou cacher
`getInstrumentSettings(deviceId, channel)` côté router (invalider sur
`instrument_settings_changed`).

### 11. `MidiRouter._getRelativeCompensation` re-itère les routes par source à chaque message
**Catégorie** : perf
**Localisation** : `src/midi/routing/MidiRouter.js:492-511`.

L'index `routesBySource` règle la diffusion, mais le calcul du
`maxComp` dans `_getRelativeCompensation` parcourt toutes les routes de
la source pour chaque message MIDI émis et appelle
`_getRouteCompensation` (cache HIT, OK) sur chacune. Sur un cours
violon → 3 destinations × 100 msgs/s × 3 lookups = mesurable.

**Fix** : memoizer `_maxRelCompBySource[source]` invalidé sur
`addRoute` / `deleteRoute` / `enableRoute` / `instrument_settings_changed`.

### 12. `Application._createAppFacade` créé avant la moitié des services
**Catégorie** : archi
**Localisation** : `src/core/Application.js:199`.

```js
const deps = this._createAppFacade();
this.container.register('app', deps);
this._registerService('database', new Database(deps));
```

Le Proxy résout au moment du `.foo`, donc OK pour les usages lazy
(`deps.deviceManager.sendMessage` plus tard). Mais plusieurs
constructeurs capturent en eager : `new MidiRouter(deps)` ligne 218
lit `deps.deviceRouteRepository` dans son ctor (ligne 45 de MidiRouter).
La ligne 207 enregistre la repo *juste avant*, ce qui marche, mais
le coupling est implicite. Un futur réordonnancement cassera le boot
en silence.

**Fix** : ne pas accéder à `deps.foo` dans les ctors ; soit prendre
un `deps` minimal avec destructuring, soit faire `deps.deviceRouteRepository`
juste-in-time. Documenter le contrat à l'entrée des sections de
`initialize()`.

### 13. Handler `error` global du logger fait planter sur reason non-Error
**Catégorie** : correctness / errors
**Localisation** : `src/core/Application.js:416-420`.

```js
['error', (error) => { this.logger.error(`Application error: ${error.message}`); }]
```

Si quelqu'un fait `eventBus.emit('error', 'oops')` ou
`eventBus.emit('error', null)`, on lit `.message` sur un string/null
→ throw, attrapé par `EventBus.emit` mais avec une stack
incompréhensible (« Cannot read properties of null »). Petit, mais
masque les vraies erreurs.

**Fix** : `error?.message ?? String(error)`.

### 14. `Logger.format` drop les payloads falsy
**Catégorie** : correctness
**Localisation** : `src/core/Logger.js:144`.

`if (data)` zappe `0`, `''`, `false`, `null`. Pour un logger
opérationnel c'est dangereux : `logger.warn('count below threshold:', 0)`
n'écrit pas la valeur. Convention attendue : `if (data !== null && data !== undefined)`.

### 15. `InstrumentManagementPage` injecte du HTML via inline `onclick`
**Catégorie** : security / archi
**Localisation** : `public/js/features/InstrumentManagementPage.js:598`.

```html
onclick="…openDeviceSettings('${escAttr(deviceId)}', '${escAttr(rawDeviceName)}')"
```

`escAttr` ne re-échappe que les `'` (déjà encodés par `escapeHtml` en
`&#39;`). Les autres séparateurs string (`\\`, `\n`) passent. À ce
jour `deviceId`/`rawDeviceName` viennent du backend (cleanish), mais
le pattern est fragile pour de futures sources (BLE advertised names,
custom user names…). Préférer `addEventListener` + `dataset`.

### 16. `HotspotConfigRepository` reçoit le handle DB brut
**Catégorie** : archi
**Localisation** : `src/core/Application.js:314`,
`src/repositories/HotspotConfigRepository.js:25`.

```js
new HotspotConfigRepository(this.database.db)
```

Toutes les autres repositories reçoivent l'objet `database` (façade) ;
celle-ci reçoit `database.db` (better-sqlite3 brut). Couplage fort
au connector, viole le contrat ADR-002.

**Fix** : passer `this.database`, adapter le ctor pour accepter la
façade.

### 17. `BlobStore.gcOrphans` peut supprimer un blob fraîchement référencé
**Catégorie** : correctness
**Localisation** : `src/files/BlobStore.js:148-172`.

Entre `isReferenced(rel) === false` et `fs.unlinkSync(…)`, un upload
concurrent peut dédupliquer et insérer dans `midi_files.blob_path`.
Comme `write()` retourne early si le fichier existe (ligne 64) sans
incrémenter de refcount, on supprime un blob référencé. Race fenêtrée
mais réelle.

**Fix** : `gcOrphans` doit prendre un `database.transaction(() => …)`
qui re-vérifie immédiatement avant l'unlink, ou mettre un lock global
upload/gc, ou shifter le check à « grace period > age_blob_file ».

### 18. Origin check WS faux-positif quand le `Host` header est forgé
**Catégorie** : security
**Localisation** : `src/api/WebSocketServer.js:91-105`.

L'auth bypasse l'API token si `originHost === serverHost && originPort === srvPort`.
Si l'attaquant force le `Host` header à la valeur de son `Origin`
(possible avec un client custom, pas avec un navigateur), il passe la
porte. À combiner avec le finding #5 (token vide), c'est exploitable.

**Fix** : comparer `req.headers.origin` à une whitelist statique
(`config.server.host` + `localhost`/`127.0.0.1`), pas au `Host`
header inbound.

## Patterns récurrents

- **`if (data) { … }`** comme guard pour data optionnel (`Logger.format`,
  plusieurs commandes WS) — drop accidentellement `0`, `''`, `false`.
  Pattern à remplacer par `if (data != null)` partout.
- **Lookup DB sur hot path** — `MidiRouter.broadcastMonitorEvent`,
  `MidiRouter._getRelativeCompensation` (cache HIT mais loop),
  `PlaybackScheduler` (cf. `CompensationService` 30s sweep).
  Investir dans le caching de `CapabilityResolver` ailleurs.
- **`innerHTML = …` avec interpolation directe** dans la majorité des
  modals. Risque XSS contained tant que les sources sont backend, mais
  pas robuste face à des noms d'instruments tirés de SysEx / BLE
  advertised names.
- **Cleanup oublié au démontage** — `FilterManager.destroy()`,
  `WebSocketServer.heartbeatInterval` (non-unref). Convention DI à
  documenter (« si vous tenez un setInterval / des listeners DOM,
  exposez `destroy()` ET un caller le branche »).
- **Constructeurs qui font du I/O ou lisent leurs deps eagerement** —
  `MidiRouter`, `Database`, plusieurs repositories. Cumulé au Proxy
  facade, ça crée des dépendances d'ordre invisibles dans
  `Application.initialize()`.
